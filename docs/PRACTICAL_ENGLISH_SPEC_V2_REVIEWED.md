## 4. Canonical Word Reference

A `WordRef` is a string that identifies exactly one vocabulary item across the whole app.

| Source | Format | Example |
|---|---|---|
| Built-in dataset | `WordItem.id` as stored in the asset | `ngsl_2809_0001` |
| Custom dataset | `<datasetId>/<WordItem.id>` | `custom_1728371234567/custom_3_918273` |

Facts and rules:

- Built-in IDs are `<datasetId>_<4-digit 0-based index>` and are globally unique. They are never renumbered.
- Custom `WordItem.id` values (`custom_<row>_<hash>`) can repeat across custom datasets, so custom words must always be qualified with their dataset ID.
- `/` is reserved as the separator; built-in IDs never contain `/`.
- Resolution: `WordRef → (dataset, WordItem)` through a map built in memory when Practical English loads. Unresolvable refs are kept, hidden from learning, and counted as "unresolved" (for example, a custom dataset that was deleted). They are not deleted.
- The same surface word can appear in several built-in lists (4,185 items, 3,439 unique forms). Each item keeps its own WordRef. At **authoring time** the content pipeline links a sentence to every built-in WordRef whose surface form is the target word. The app never guesses links at runtime.

## 5. V1 → V2 Migration Layer

### 5.1 V1 legacy state (read as-is; keys are never renamed or retyped)

| V1 key | Type | Meaning |
|---|---|---|
| `starred_v1_<datasetId>` | StringList of indexes | ★ 不熟悉 (unfamiliar) |
| `stats_all_learned_v1` | StringList of `<datasetId>:<index>` | item was spoken at least once (exposure) |
| `progress_v1_<datasetId>` | JSON | playback position (not migrated; V1-only) |
| `settings_v1` | JSON | playback settings (V1-only) |

V1 has no explicit "familiar" flag; "not starred" is its familiar state. V2 does not invent one from V1 data.

### 5.2 Model

```
V1 legacy state (index-based)
        ↓  Migration Layer (index → WordRef via current datasets)
V2 canonical state (WordRef-based, V2 namespace)
        ↓
Practical English
```

After migration, V2 logic reads and writes only canonical state. V1 keeps working on indexes unchanged.

### 5.3 Dataset fingerprint

For every dataset, `fingerprint = FNV-1a 64 over the ordered list of WordItem.id joined by "\n"`. The fingerprint stored with each sync shows whether the index→ID mapping that V1 used is still the same.

The item count is stored with the fingerprint. A dataset is **compatible** with the last sync when the fingerprint of its first `count` items equals the stored fingerprint: unchanged and append-only datasets keep every old index valid. Anything else (reorder, insert, delete) is **changed**. A dataset with no stored fingerprint (first sync, or a newly imported custom dataset) is treated as compatible.

### 5.4 Timing

1. **Initial migration**: the first time Practical English loads (lazy, not during V1 startup).
2. **Reconciliation**: every later Practical English load, to bring in ★ changes the user made in V1 since the last sync.

### 5.5 Mapping rules

For each dataset (built-in and custom):

- `index → items[index].id`, qualified to a WordRef per §4.
- Initial migration:
  - V1 ★ indexes → `weak = true`.
  - V1 learned `<datasetId>:<index>` → `exposedInV1 = true` (exposure only, **never** mastery).
- Reconciliation:
  - **Compatible** since the last sync (§5.3): V1 ★ is authoritative. Replace that dataset's canonical `weak` set with the mapped V1 ★ set.
  - **Changed** (content order changed, §5.3): do not trust index mapping. Keep the canonical `weak` set, and write it back to `starred_v1_<datasetId>` using the new indexes (repair). Log the event.
- Store the new fingerprint per dataset after a successful sync.

### 5.6 Unresolved items

- An index outside the dataset's range, or a dataset ID that no longer exists, is recorded in `migration_state.json → unresolved` with its source key and raw value.
- Unresolved items are never deleted from V1 keys and never block migration. They are retried on the next reconciliation.
- The count is available to debug/diagnostics only; no user-facing error.

### 5.7 Versioning, idempotency and failure

- SharedPreferences key `pe_migration_version` (int). Current value: `1`.
- Migration runs only when `pe_migration_version < 1`. It sets the key **after** canonical state has been written successfully.
- Migration is idempotent: running it twice from the same V1 data produces the same canonical state (set semantics, no counters).
- If migration fails partway: the version key is not written, canonical state on disk stays as it was (atomic write, §7.3), and the next load retries. V1 data is never modified by the initial migration.
- Reconciliation is also idempotent and runs every load; it has no version gate.

### 5.8 Content rule (still required for V1)

V1 itself still uses indexes, so built-in datasets stay **append-only**: no inserting, deleting or reordering items, including through Firebase Storage content updates. V2 does not rely on this rule (it detects reorders by fingerprint), but V1 display does.

## 6. Sentence model

### 6.1 Fields

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | String | yes | Sentence ID, §6.2 |
| `wordIds` | List<String> | yes, ≥1 | WordRefs, §4. Only persisted relationship |
| `datasetId` | String | yes | Sentence source, e.g. `pe_core`, or `pe_import` for user imports |
| `targetLanguage` | String | yes | Same format as `WordDataset.wordLocale`, e.g. `en-US`. Used as TTS language |
| `sentenceText` | String | yes | The sentence to learn |
| `translations` | Map<String,String> | yes (may be empty) | Locale keys use the **same codes as WordItem translations**: `zh-TW`, `zh-CN`, `ja`, `ko`, `vi`, `id`, `es`, `pt-BR`, `th`, `ar` |
| `level` | String? | no | e.g. `A1`–`C2` |
| `category` | String? | no | e.g. `daily`, `work` |
| `patternId` | String? | no | Reserved for V2.1; always null in V2.0 |
| `scenarioId` | String? | no | Reserved for V2.2; always null in V2.0 |
| `metadata` | Map<String,dynamic>? | no | Free-form notes only. Never used for anything that needs querying |

`translationLocale` and `translationText` are **not** used.

Translation fallback (same as V1 `WordItem.resolveLocale`): UI locale → `zh-TW` → first available → none (show English only).

Example:

```json
{
  "id": "pe_core_000001",
  "wordIds": ["ngsl_2809_0001", "ngsl_spoken_720_0004"],
  "datasetId": "pe_core",
  "targetLanguage": "en-US",
  "sentenceText": "I need more time.",
  "translations": { "zh-TW": "我需要更多時間。" },
  "level": "A1",
  "category": "daily",
  "patternId": null,
  "scenarioId": null
}
```

### 6.2 Sentence ID Factory

| Source | Format | Rule |
|---|---|---|
| Built-in content | `pe_core_` + 6-digit serial (`pe_core_000001`) | Assigned once by the content pipeline. Never reused or renumbered |
| Imported | `imp_` + 16 lowercase hex chars | `FNV-1a 64(dedupKey)` |

- `dedupKey = targetLanguage + "\u0001" + normalize(sentenceText)`.
- `normalize`: Unicode NFC → trim → collapse internal whitespace to one space → map curly quotes/apostrophes to straight ones → remove trailing `.`, `!`, `?`, `。`, `！`, `？` → lowercase.
- NFC implementation note (2026-10-08): Dart has no built-in Unicode NFC normalization, and V2.0 adds no package for it. The V2.0 implementation applies every other step above, all of which Dart runs reliably and identically on every device, so Sentence IDs stay deterministic and stable. Imported CSV text is almost always NFC already. If cross-source or multilingual content later needs Unicode canonical normalization, a dedicated package will be evaluated then; adding it would change `normalize` and therefore requires an ID-stability migration plan first.
- FNV-1a 64 is implemented in Dart (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`, over UTF-8 bytes). No new package. `String.hashCode` is never used for any persisted ID.
- The two prefixes guarantee built-in and imported IDs never collide.
- **Collision handling**: the importer keeps an in-memory `dedupKey → id` index. If a generated ID already belongs to a different dedupKey, append `-2`, `-3`, … until free. Because lookup is by dedupKey first, re-importing returns the already-assigned ID, so the result stays stable.

### 6.3 Relationship and reverse index

- `Sentence.wordIds` is the only persisted Sentence↔Word link. No Word→Sentence data is saved anywhere.
- On load, `SentenceRepository` builds `Map<WordRef, List<SentenceId>>` in memory once, and rebuilds it after an import. It is discarded with the repository.

## 7. Storage

### 7.1 Locations

| Data | Location | Written by |
|---|---|---|
| Built-in sentences | `assets/practical_english/pe_core.json` (read-only) | content pipeline |
| Imported sentences | `<appDocuments>/practical_english/imported_sentences.json` | importer |
| Canonical word state | `<appDocuments>/practical_english/word_state.json` | PracticalEnglishState |
| Migration state (fingerprints, unresolved) | `<appDocuments>/practical_english/migration_state.json` | Migration Layer |
| Small flags | SharedPreferences keys prefixed `pe_` plus the two What's New keys in §11 | various |

Large data is never stored in SharedPreferences (Android loads all of SharedPreferences into memory at startup).

### 7.2 Word state record

```json
{ "schema": 1,
  "words": {
    "ngsl_2809_0001": { "weak": true, "mastered": false, "exposedInV1": true,
                        "peExposureCount": 3, "lastPracticedAt": "2026-10-08T12:00:00Z" } } }
```

Only words with some state are stored. Absent = unseen.

### 7.3 Writing (one shared `JsonFileStore` helper)

1. Write the full JSON to `<file>.tmp` and flush.
2. If `<file>` exists, rename it to `<file>.bak`.
3. Rename `<file>.tmp` to `<file>`.
4. Writes are debounced (2 s). Pending writes flush immediately when the app goes to background (`AppLifecycleState.paused`) and when leaving Practical English.

### 7.4 Reading and corruption recovery

1. Parse `<file>`. If it is missing or fails to parse, parse `<file>.bak`.
2. If both fail, rename the bad file to `<file>.corrupt-<timestamp>` (kept for diagnosis), start from an empty state, and record a non-fatal error with the existing Crashlytics integration. For `word_state.json`, the next reconciliation rebuilds `weak` from V1 ★, so the user's weak words are not lost.
3. Missing files on first run are normal and are not errors.

### 7.5 Memory lifecycle

- Load → parse (large JSON in a background isolate via `compute()`) → keep in the repository's memory while Practical English is in use.
- Nothing is loaded during V1 startup.
- No separate CacheManager, singleton cache framework or eviction logic in V2.0.

## 8. CSV import

### 8.1 Format B (V2.0)

Header row is required. Columns:

```
word_id,sentence,sentence_translation[,target_language,translation_locale,level,category]
```

```csv
word_id,sentence,sentence_translation
ngsl_2809_0001,I need more time.,我需要更多時間。
ngsl_2809_0001|ngsl_2809_0120,I need some help with this.,這件事我需要一些幫忙。
```

- `word_id` holds one or more WordRefs separated by `|`.
- Defaults: `target_language = en-US`; `translation_locale` = the locale chosen on the import screen; `level` and `category` empty.
- Reuses the existing CSV parsing behavior (BOM removal, newline normalization, delimiter detection).
- No AI is called during import.

### 8.2 Row validation (in order)

1. Missing required column or empty `sentence` → **Invalid Row**.
2. Any WordRef that does not resolve → **Invalid Word ID**; the whole row is rejected and listed with the bad IDs. No partial linking.
3. Compute `dedupKey`:
   - New key → **Added** (new imported Sentence with an ID per §6.2).
   - Existing key with new WordRefs not yet linked → **Updated** (merge WordRefs into `wordIds`; existing translations are kept).
   - Existing key with a translation for a locale that has none yet → **Updated** (add that locale).
   - Otherwise → **Duplicate** (nothing changes; an existing different translation is not overwritten).
4. Built-in sentences are never modified by import. A row matching a built-in sentence's dedupKey is a **Duplicate**.

### 8.3 Guarantees

- Idempotent: importing the same file twice gives Added = 0 and Updated = 0 the second time.
- The whole file is validated in memory first, then written with one atomic write. A failed write leaves the previous data intact.
- Summary shown to the user: **Added / Updated / Duplicate / Invalid Word ID / Invalid Row**, with row numbers for the last two.
- A file-level hash can skip unchanged files as an optimization only; sentence-level dedup is still authoritative.

### 8.4 Format A (deferred, not in V2.0)

`word,translation,sentence,sentence_translation` is not supported in V2.0. If added later, it must: resolve words strictly; show a preview; mark ambiguous words (multiple matches) and unmatched words; and create links only after the user confirms each one. It never links silently.

## 9. Learning model

### 9.1 Word learning status (derived, per WordRef)

| Status | Condition (first match wins) |
|---|---|
| `mastered` | `mastered == true` |
| `weak` | `weak == true` |
| `learning` | `peExposureCount > 0` |
| `seen` | `exposedInV1 == true` |
| `unseen` | none of the above |

Exposure (played, seen) never counts as mastery.

### 9.2 Weak Word = V1 ★

- `weak` is the same user signal as V1 ★ 不熟悉.
- Marking or unmarking weak in Practical English updates canonical state **and** writes the V1 ★ set for that dataset (same key, same type, through `ProgressRepository.saveStarred`), so V1 and V2 always agree.
- Changes made in V1 reach V2 through reconciliation (§5.5).

### 9.3 Mastery

- Only the manual action "我會了" sets `mastered = true`. It also clears `weak` (and so the V1 ★).
- Marking a mastered word weak again clears `mastered`.
- No SM-2, FSRS, automatic scoring or spaced repetition in V2.0.

### 9.4 Learning modes and sentence selection (deterministic, local)

Modes: **All words** / **Weak priority** / **Weak only**.

For each candidate sentence:

`score = 3 × (weak words in wordIds) + 1 × (unseen/seen/learning words in wordIds)`

- Weak only: candidates must contain ≥1 weak word.
- Weak priority: all candidates, sorted by score descending.
- All words: all candidates, sorted by sentence order (or shuffled with the existing `PlaylistBuilder.shuffle` if shuffle is on).
- Ties: oldest `lastPracticedAt` first, then sentence ID.
- One sentence containing several weak words strengthens all of them; practicing it increments `peExposureCount` for every word in `wordIds`.
- Practice in Practical English does not change V1 statistics (`stats_*` keys).

### 9.5 Learning coverage

- Per dataset and overall (4,185 built-in items plus custom items):
  - **Available**: words with ≥1 resolvable sentence.
  - **Practiced**: words with `peExposureCount > 0`.
  - **Mastered**: words with `mastered == true`.
- Shown as counts and percentages. Words with no sentence yet count as "not available", not as failures.

## 10. TTS and PlaybackCoordinator

- V2.0 uses the existing `SystemTtsService` (`flutter_tts`) instance. Same speech rate and pinned voice as V1. No audio files, no cloud TTS.
- `PlaybackCoordinator` is a small class holding the current owner: `none | v1 | v2`.

Rules:

- `claim(v2)`: if the owner is V1, call `AppState.stopCruise()` and `TtsService.stop()`, then set the owner to V2.
- `claim(v1)`: if the owner is V2, stop V2 playback and `TtsService.stop()`, then set the owner to V1.
- V1 calls `claim(v1)` at the start of `startCruise()` and before any manual speak (`next`/`previous`/`replay`/`jumpTo`). These are the only V1 code changes; V1 behavior is otherwise unchanged.
- Only one speech owner exists at any time.

Not changed in V2.0:

- `TtsAudioHandler` / audio_service architecture.
- Lock-screen and notification controls stay bound to V1 cruise. Pressing play there claims V1 and stops V2.
- No V2 lock-screen controls and no V2 background playback.

## 11. What's New

| Concept | Key / source | Example | Purpose |
|---|---|---|---|
| App version | `pubspec.yaml` version | release version | Store/build only |
| Data schema version | SharedPreferences `app_schema_version` (int) | `2` | Which persisted data model this install has |
| What's New version | SharedPreferences `last_seen_whats_new_version` (String) | `pe_2_0` | Which introduction the user has already seen |

The three are independent. The What's New ID is a content ID, not tied to the app version string.

Startup logic (runs once per launch, cheap):

1. If `app_schema_version` is missing:
   - If any V1 data exists (`onboarding_seen_v1` or `settings_v1` present) → this is a V1 user upgrading → set `app_schema_version = 2` and leave `last_seen_whats_new_version` unset, so What's New shows.
   - Otherwise (fresh install) → set `app_schema_version = 2` and `last_seen_whats_new_version = pe_2_0`. The new user sees the normal onboarding, not What's New.
2. If `last_seen_whats_new_version != pe_2_0` → show What's New once (Practical English, Sentence Learning, Weak Word Learning, where to find the entry), then set it to `pe_2_0`.
3. What's New can be opened again any time from the menu (Settings / About → What's New).

V1 data is never reset. `settings_v1` is used only as evidence that V1 data exists, never to track What's New.

## 12. Premium and monetization

- Same RevenueCat entitlement `premium`, same products and prices. No `sentence_pro`, `v2_pro` or second subscription system.
- Free tier (product rule A, confirmed by Lawrence 2026-10-09): a sentence is available to a free user only if **every target word** in it is unlocked. A target word may be linked through several WordRefs in different lists (§4); it counts as unlocked if **any** of its WordRefs in the sentence's `wordIds` is within that dataset's `unlockedCount()` range.
  - "The same target word" is decided only among the sentence's own `wordIds`: WordRefs whose items have the same source language (`wordLocale`) and the same surface form (trimmed, case-insensitive). No WordRef outside `wordIds` is ever considered.
  - Any unresolvable WordRef hides the sentence (§4), whether or not the word is unlocked elsewhere.
  - Imported sentences follow the same rule through their linked words. Premium users have everything.
- Ads in Practical English follow V1's conservative policy: no new ad formats or placements beyond what V1 already uses.
- Future price changes: new subscribers may get new prices; existing subscribers may be grandfathered. That is a product decision outside V2.0.

## 13. Content strategy

- Built-in corpus `pe_core` is original content: AI drafts **at authoring time** plus human proofreading, owned by the developer. No unlicensed third-party sentences.
- First batch: NGSL 2,809 items 1–1,000 (by list order) × about 1 sentence per word, English + zh-TW.
- The content pipeline (outside the app) validates every WordRef, assigns `pe_core_` IDs, links all built-in items with the same surface form (§4), and outputs `assets/practical_english/pe_core.json`.
- Expand to all 4,185 items only after the first batch passes the checks in §16.
- Language: English + zh-TW in V2.0. The model is multilingual-ready (other locales are only additional `translations` entries). UI strings for Practical English are still provided in all 11 app languages.

## 14. Performance

- V1 startup is not affected (Practical English loads lazily).
- Expected sizes: ~1,000 sentences in V2.0 (< 0.5 MB); full 4,185+ sentences × 10 locales ≈ 3 MB JSON. Parsing in a background isolate keeps the UI responsive.
- The reverse index and the selector run in memory over ≤ ~10,000 sentences; no database needed.
- Word state is written with debounce (§7.3), never once per spoken word.
- SQLite/Drift/Isar would be reconsidered only if measured load time or memory becomes a real problem (for example, full-text search or large downloadable packs).

## 16. V2.0 scope and acceptance criteria

### In scope

1. Sentence model, WordRef, Sentence ID Factory
2. SentenceRepository with built-in assets and imported JSON
3. Migration Layer and reconciliation
4. CSV Format B import with validation, dedup and summary
5. Sentence list/detail UI and word → sentence linking
6. Sentence TTS through PlaybackCoordinator
7. Weak Word (shared with V1 ★), manual mastery, three learning modes, coverage
8. Independent PracticalEnglishState
9. What's New
10. First content batch (NGSL 1,000 words, English + zh-TW)

### Acceptance criteria

- **V1 safety**: upgrading a device with V1 data keeps all ★, learned stats, playback position, settings, custom datasets, reminders and Premium state, verified by installing V2 over V1 v19 on a real device.
- **Migration**: every V1 ★ shows as weak in V2; running migration twice changes nothing; an out-of-range index ends up in `unresolved` without errors.
- **Weak sync**: ★ set in V1 appears as weak in V2 on next entry, and weak set in V2 appears as ★ in V1.
- **Import**: a test file covering Added / Updated / Duplicate / Invalid Word ID / Invalid Row produces the exact expected counts; re-importing gives Added = 0, Updated = 0.
- **IDs**: Sentence IDs for the same input are identical across app restarts and devices (unit test with fixed expected values).
- **Playback**: starting V2 speech while V1 cruise is playing stops V1 first; pressing lock-screen play stops V2. Speech never overlaps.
- **Storage**: a corrupted `word_state.json` falls back to `.bak` or empty without a crash, and weak words return after reconciliation.
- **What's New**: shows once for an upgraded V1 user, not for a fresh install, and can be reopened from the menu.
- **Premium**: free users see only sentences whose words are unlocked; Premium sees all.
- **Performance**: entering Practical English with the first content batch shows the first screen without visible lag on a mid-range Android device; V1 startup time is unchanged.
- **Tests**: unit tests for ID factory, normalize/dedup, importer, migration mapping/reconciliation and selector.

### Explicitly not in V2.0

- SQLite / Drift / Sqflite / Isar
- Runtime AI sentence generation or conversation
- SRS, SM-2, FSRS, automatic mastery scoring
- ASR, speaking scoring
- V2 lock-screen controls, V2 background playback, audio_service refactoring
- Separate V2 entitlement or pricing
- Cache framework
- CSV Format A
- Full multilingual sentence content
- Pattern / Scenario engines (only the nullable fields exist)
- Cloud sync / accounts
- Any change to Firebase, RevenueCat, AdMob, Play settings, GitHub Actions or Application ID

## 17. Branch and release rules

- `main` = V1 stable/production. V2 code is developed on `feature/practical-english-v2` (created when coding is approved) and is not merged into `main` until V2.0 is verified.
- V2 test APKs: run the existing build workflow manually on the V2 branch (no workflow change). Test AABs from the V2 branch are never uploaded to Play. The versionCode is decided at merge time.
